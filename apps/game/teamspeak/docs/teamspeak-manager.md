# TS6 Manager

Дата развёртывания: 2026-09-05.

## Размещение

- Приложение: `clusterzx/ts6-manager`.
- Узел: тот же выделенный Docker-host TeamSpeak; приватный адрес в публичной копии не фиксируется.
- Стек Dockhand: internal stack `ts6-manager` в окружении `120 - TeamSpeak` (ID окружения `21`).
- Compose-файл: `/home/Dockhand/data/stacks/120 - TeamSpeak/ts6-manager/compose.yaml` на узле Dockhand.
- Файл окружения: `/home/Dockhand/data/stacks/120 - TeamSpeak/ts6-manager/.env` на узле Dockhand.
- Рабочая копия Hawser: `/data/stacks/ts6-manager/{compose.yaml,.env}` внутри контейнера `hawser` на узле TeamSpeak.
- Постоянная база SQLite: `/home/teamspeak/ts6-manager/backend-data/ts6webui.db`.
- Музыкальная библиотека: `/home/teamspeak/ts6-manager/music`.
- Постоянные исполняемые компоненты музыки: `/home/teamspeak/ts6-manager/bin/{yt-dlp,deno}`.
- Плагин и конфигурация `yt-dlp`: `/home/teamspeak/ts6-manager/yt-dlp-plugins/` и `/home/teamspeak/ts6-manager/yt-dlp-config`.
- Общая Docker-сеть компонентов: внешняя `frontend`; backend дополнительно использует изолированную исходящую сеть `ts6-manager-egress`.

Стек создан и развёрнут штатным API Dockhand через Hawser. В `/home/teamspeak` нет `compose.yaml` или `.env`: на целевом узле находятся только постоянные данные TeamSpeak и TS6 Manager.

## Компоненты

| Сервис | Контейнер | Образ | Публикация |
|---|---|---|---|
| Web UI | `ts6-manager-frontend` | `clusterzx/ts6-manager:frontend` | `3000/tcp` -> `80/tcp` |
| Backend | `ts6-manager-backend` | `clusterzx/ts6-manager:backend` | сети `frontend` и `ts6-manager-egress`, порт `3001/tcp` не опубликован |
| WebRTC sidecar | `ts6-manager-sidecar` | `clusterzx/ts6-manager:sidecar` | только сеть `frontend`, порт `9800/tcp` |
| YouTube PO Token provider | `ts6-manager-bgutil-provider` | `brainicism/bgutil-ytdlp-pot-provider:1.3.2` | только сеть `frontend`, порт `4416/tcp` не опубликован |
| Внутренний диспетчер | `ts6-manager-request-music-controller` | `node:20-alpine` | музыка по запросу и подтверждение новичков; только сеть `frontend`, порт `3100/tcp` не опубликован |

Интерфейс доступен по адресу из `FRONTEND_URL`; первичная регистрация администратора выполняется на `/setup`. JWT-подпись и отдельный ключ шифрования должны быть сгенерированы случайно и сохранены как секретные переменные Dockhand. Реальные значения не фиксируются в публичном репозитории.

Для всех контейнеров включены `restart: unless-stopped`, `no-new-privileges` и ограничение Docker-логов до трёх файлов по 10 MiB. Backend и sidecar не опубликованы на интерфейсах узла.

## Интеграция с TeamSpeak

В менеджер добавлено активное соединение `Ammatias Game Hub` с внутренним адресом `teamspeak`, WebQuery HTTP `10080` и SSH Query `10022`. Для менеджера выпущен отдельный API key области `manage` со сроком действия 3650 дней; ранее созданный неиспользуемый ключ удалён. API key и пароль `serveradmin` хранятся в базе TS6 Manager в зашифрованном формате AES-256-GCM и в документации не фиксируются.

HTTP и SSH Query включены в стеке TeamSpeak через Dockhand, но не опубликованы на интерфейсах хоста. Backend обращается к ним по общей сети `frontend`. В Query allowlist добавлена подсеть `172.18.0.0/16`: без неё серия запросов Dashboard могла завершаться `socket hang up` из-за защиты от флуда. Глобальное отключение защиты не используется.

## AFK-поток

Поток `AFK Mover` включён и запускается каждую минуту. Клиенты с бездействием от 300 секунд перемещаются в канал AFK с ID `16`. Для музыкальных ботов создана постоянная серверная группа TeamSpeak `Bots` с ID `9`; её ID указан в `exemptGroupIds`, поэтому участники этой группы не переносятся в AFK. Текущий `MusicBot` (client database ID `8`) добавлен в группу `Bots`.

Группе `Bots` точечно выданы `b_channel_join_permanent=1` и `i_client_move_power=25`. Первое право необходимо потому, что отдельная серверная группа не получает полный набор разрешений Guest, а музыкальный канал постоянный. Второе требуется реализации голосового клиента TS6 Manager: после подключения она выполняет `clientmove` в настроенный канал. Без права входа сервер возвращал `TS3 error 2568` с `failed_permid=138`, после чего дефект текущей версии менеджера запускал частые повторные подключения и TeamSpeak временно блокировал клиента.

При создании нового музыкального бота его также следует добавить в серверную группу `Bots`: исключение потока основано на членстве в группе, а не на имени клиента.

## Музыкальный бот по запросу

Создан второй голосовой бот `RequestMusicBot` (отображаемое имя `MusicBot Request`, client database ID `14`). Он состоит в серверной группе `Bots`, имеет `autoStart=false` и в обычном состоянии отключён от TeamSpeak.

Поток `Request Music Bot` (ID `2`) слушает команду `!play <URL>` в обычных голосовых каналах с ID `6, 9, 10, 17, 11, 12, 13, 14, 20, 15`. Канал `💬 Музыка` (ID `18`), AFK, лобби и главные каналы-разделители не включены. В `💬 Музыка` команду продолжает обслуживать постоянный MusicBot.

При первом запросе внутренний диспетчер подключает `MusicBot Request` к каналу автора и передаёт URL штатному API воспроизведения TS6 Manager. Последующие команды в том же канале принимает уже встроенный обработчик подключённого бота и добавляет треки в его очередь. Запросы из других каналов ставятся диспетчером в последовательную очередь. Через шесть секунд после завершения последнего трека бот отключается; затем, если очередь диспетчера не пуста, подключается к следующему каналу.

Диспетчер хранится в `/home/teamspeak/ts6-manager/request-bot/request-music-controller.mjs` и запущен отдельным непубликуемым контейнером. Для обращения Bot Engine к нему используется точечный allowlist `TS_INTERNAL_HTTP_HOSTS=request-music-controller`: изменённый `url-validator.js` разрешает только это явно указанное внутреннее имя, а исходная SSRF-защита для остальных приватных и metadata-адресов сохранена. Оба файла подключены к контейнерам read-only; Compose управляется только через Dockhand.

## Подтверждение новых пользователей

Для допуска новых пользователей используется постоянная серверная группа `Verified` с ID `10`. Она создана копированием прежнего набора разрешений Guest и предоставляет базовые права: вход в обычные каналы, голос, чат и стандартные клиентские операции. Все существовавшие обычные пользователи заранее перенесены в `Verified`; Server Admin и музыкальные боты сохранили собственные группы.

Группа по умолчанию Guest (ID `8`) очищена от прежних 34 разрешений. У неё оставлено только техническое `b_virtualserver_token_use=1`, необходимое для применения одноразового ключа подтверждения. Новый клиент может подключиться только в канал по умолчанию `🏠 Лобби`, где голос запрещён требованием talk power `100`; он не может переходить в постоянные каналы, говорить, писать сообщения, создавать каналы или пользоваться файлами. В `AFK Mover` группы `8` и `9` указаны как исключения, поэтому неподтверждённый гость остаётся в лобби, а музыкальные боты — в своих каналах.

Поток `Guest Verification` (ID `3`) реагирует на `notifycliententerview` и передаёт ID нового клиента внутреннему диспетчеру. Для клиента только из группы Guest диспетчер создаёт штатный одноразовый TeamSpeak privilege key группы `Verified` и отправляет приватное приветствие с BBCode-ссылкой-кнопкой `✅ Подтвердить и получить базовые права`. Ссылка использует URI `teamspeak://ts.ammatias.ru` и содержит порт, пароль подключения и персональный ключ; пароль не выводится в логах или документации. Нажатие запускает TeamSpeak, повторно подключает пользователя и применяет ключ во время `clientinit`, после чего постоянная группа меняется с Guest на `Verified`.

При повторном входе неподтверждённого пользователя диспетчер удаляет ранее выпущенный незадействованный ключ и создаёт новый. После успешного применения TeamSpeak автоматически удаляет одноразовый ключ. Подтверждение не требует веб-страницы, опубликованного HTTP endpoint или учётной записи TS6 Manager; прежний reverse proxy `/confirm` удалён.

## Воспроизведение YouTube

Встроенная в образ версия `yt-dlp` `2026.03.03` заменена bind-mount на проверенный официальный выпуск `2026.08.19`. Для JavaScript challenge используется Deno `2.9.6`, поскольку Node.js 20 из образа ниже минимальной версии Node.js 22, поддерживаемой актуальным `yt-dlp`. Для выдачи GVS PO Token подключён плагин `bgutil-ytdlp-pot-provider` `1.3.2` и внутренний одноимённый HTTP provider; `yt-dlp` настроен на клиент `mweb` и принудительный IPv4.

Для backend создана отдельная исходящая сеть `ts6-manager-egress` с MTU `1492` и более высоким приоритетом шлюза. Сеть `frontend` сохранена для доступа к TeamSpeak, sidecar и provider. Включены TCP MTU probing и базовый MSS `1400`. Для проблемного CDN-узла `rr5---sn-4g5edndd.googlevideo.com`, который принимал TCP, но не завершал TLS на исходном адресе, добавлено точечное сопоставление с проверенным Googlevideo edge `173.194.164.212`; подписанный URL и TLS SNI при этом не изменяются.

## Эксплуатационные замечания

Образы проекта используют теги `backend`, `frontend` и `sidecar` без версионных тегов, поэтому текущая пилотная установка не полностью воспроизводима. Загруженные слои занимают значительный объём: после установки занято около 3.9 GiB из 7.8 GiB системного диска, свободно около 3.5 GiB. Перед длительной эксплуатацией стоит зафиксировать digest образов и следить за диском.

Все обновления, изменения и удаление стека выполнять через Dockhand в окружении `120 - TeamSpeak`.
